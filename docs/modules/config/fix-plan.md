## 详细修复方案

### P0-1: 敏感配置值明文存储

**问题描述**: 
敏感配置（API密钥、密码等）以明文形式存储在数据库中，仅在展示时脱敏。攻击者获取数据库访问权限后可直接读取所有敏感信息。

**CVSS 3.1**: 9.1 (AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:H/A:H)

**影响范围**: 
- 数据库备份泄露导致所有 API 密钥、密码暴露
- 内部人员可直接查询敏感配置
- 不符合 PCI-DSS、GDPR 合规要求

**修复方案**:
1. 创建加密服务 `ConfigEncryptionService`，使用 AES-256-GCM 加密
2. 实现 JPA AttributeConverter `SensitiveConfigConverter`
3. 修改 `SysConfig` Entity 使用加密转换器
4. 配置加密密钥通过环境变量 `CONFIG_ENCRYPTION_KEY` 注入
5. 数据迁移：加密现有敏感配置值

**验证方法**:
- 直接查询数据库，验证敏感配置值已加密
- 通过 API 查询，验证能正确解密并脱敏展示
- 测试加密密钥错误时的异常处理

**工作量**: 2.0 人日

### P0-2: 配置历史记录明文敏感值

**问题描述**: 
配置变更历史表记录了 `old_value` 和 `new_value`，对于敏感配置，这些历史值也是明文存储。

**CVSS 3.1**: 8.8 (AV:N/AC:L/PR:H/UI:N/S:C/C:H/I:H/A:N)

**影响范围**: 
- 即使当前配置值被删除，历史记录仍保留明文
- 审计日志成为攻击目标

**修复方案**:
1. 修改 `ConfigServiceImpl.save()` 方法
2. 敏感配置不记录明文历史，仅记录 `[REDACTED]`
3. 或使用相同的加密策略加密历史值

**验证方法**:
- 修改敏感配置，查询历史表验证值已脱敏或加密
- 测试非敏感配置历史记录正常

**工作量**: 0.5 人日

### P1-1: 缓存全量失效导致缓存雪崩

**问题描述**: 
每次保存/删除单个配置时，使用 `@CacheEvict(allEntries = true)` 清空整个缓存空间，高并发场景下导致缓存击穿。

**影响范围**: 
- 修改一个配置导致所有配置缓存失效
- 并发更新场景下，数据库查询激增（可能 20x）
- 分布式环境下，多实例缓存不一致

**修复方案**:
1. 改为精确缓存失效：`@CacheEvict(value = "config", key = "#vo.configKey")`
2. 或使用 `@CachePut` 更新缓存而非清除
3. 删除操作同样使用精确 key 失效

**验证方法**:
- 压测：修改一个配置，观察其他配置缓存是否仍然命中
- 监控数据库 QPS，验证未出现激增

**工作量**: 0.5 人日

### P1-2: 版本历史表缺少索引

**问题描述**: 
`sys_config_version_history` 表未定义在 `schema.sql` 中，查询缺少复合索引，历史记录增长后性能线性下降。

**影响范围**: 
- 配置变更历史查询（审计场景）响应时间随数据量增长
- 可能从 10ms 增长到 100ms+

**修复方案**:
1. 在 `schema.sql` 中添加表定义
2. 创建复合索引：`CREATE INDEX idx_config_version_history_config_time ON sys_config_version_history (config_id, create_time DESC)`
3. 创建操作员审计索引：`CREATE INDEX idx_config_version_history_operator ON sys_config_version_history (operator_id, create_time DESC)`

**验证方法**:
- 插入 10000 条历史记录，查询响应时间应 <20ms
- 使用 EXPLAIN ANALYZE 验证索引被使用

**工作量**: 0.5 人日

### P1-3: Controller 权限校验代码重复

**问题描述**: 
每个接口方法都重复相同的认证和权限校验逻辑（4 处重复），违反 DRY 原则。

**影响范围**: 
- 代码可维护性差，修改权限逻辑需要改动多处
- 容易遗漏某个接口的权限校验

**修复方案**:
1. 使用 Spring AOP 切面统一处理权限校验
2. 或使用 Spring Security 的 `@PreAuthorize("hasRole('ADMIN')")` 注解
3. 或提取为私有方法 `validateAdminAccess(request)` 返回 `Optional<RESTResult<?>>`

**验证方法**:
- 代码审查：确认所有接口使用统一权限校验
- 测试：非管理员访问应返回 403

**工作量**: 1.0 人日

### P1-4: 缺少关键操作审计日志

**问题描述**: 
配置的新增、修改、删除操作缺少审计日志，无法追溯谁在何时何地做了什么操作。

**影响范围**: 
- 生产环境问题排查困难
- 无法追踪配置被谁修改
- 不符合审计合规要求（SOC2、ISO27001）

**修复方案**:
1. 在 `ConfigServiceImpl.save()` 中添加审计日志
2. 记录：操作类型（CREATE/UPDATE/DELETE）、配置键、操作人、IP 地址、User-Agent、时间戳
3. 关键配置变更发送告警（如包含 password/secret/key/token）

**验证方法**:
- 修改配置，查看日志文件验证审计日志格式正确
- 验证敏感配置变更触发告警

**工作量**: 1.0 人日

### P1-5: 敏感配置脱敏算法不安全

**问题描述**: 
敏感配置仅保留后 4 位，前面用 `****` 替换。对于短密钥（如 4-8 位密码），泄露后 4 位可大幅降低暴力破解难度。

**CVSS 3.1**: 6.8 (AV:N/AC:L/PR:H/UI:N/S:U/C:H/I:L/A:N)

**影响范围**: 
- 短密钥（如 `pass1234`）显示为 `****1234`，泄露 50% 信息
- 不符合 PCI-DSS 脱敏标准（最多显示前 6 后 4 位）

**修复方案**:
1. 根据长度动态脱敏：
   - ≤8 位：完全隐藏 `********`
   - 9-16 位：仅显示前 2 位 `ab****`
   - 17-32 位：显示前 4 后 4 位 `abcd****wxyz`
   - >32 位：显示前 6 后 4 位 `abcdef******wxyz`

**验证方法**:
- 单元测试：覆盖不同长度的敏感值脱敏
- 手动测试：创建不同长度的敏感配置，验证脱敏效果

**工作量**: 1.0 人日

### P1-6: getRawValueByKey 缺少访问控制

**问题描述**: 
`getRawValueByKey()` 方法返回未脱敏的原始配置值，但仅通过注释说明"仅后端内部使用"，缺少代码层面的访问控制。

**CVSS 3.1**: 7.2 (AV:N/AC:L/PR:H/UI:N/S:U/C:H/I:H/A:N)

**影响范围**: 
- 任何模块可调用此方法获取明文敏感配置
- 无法审计哪些代码访问了敏感配置
- 违反最小权限原则

**修复方案**:
1. 添加调用者验证，使用白名单机制
2. 或使用包私有访问控制 + 自定义 `@Internal` 注解
3. 记录所有调用到审计日志

**验证方法**:
- 测试：非白名单模块调用应抛出 SecurityException
- 审计日志验证调用记录

**工作量**: 0.5 人日

### P1-7: 缺少配置值长度限制

**问题描述**: 
`config_value` 字段类型为 `TEXT`，无长度限制，恶意管理员可提交超大配置值导致数据库性能下降或内存溢出。

**CVSS 3.1**: 7.1 (AV:N/AC:L/PR:H/UI:N/S:U/C:N/I:L/A:H)

**影响范围**: 
- 恶意管理员提交 100MB 配置值导致数据库膨胀
- 查询大配置时内存溢出（OOM）

**修复方案**:
1. 在 `ConfigSaveVO` 添加 `@Size(max = 65535)` 注解（64KB 限制）
2. 在 Service 层添加字节长度校验
3. 数据库层面添加约束（可选）

**验证方法**:
- 测试：提交 65KB+ 配置值应返回错误
- 测试：提交 64KB 配置值应成功

**工作量**: 0.5 人日

---

### P1-8: 缺少 L1 Caffeine 本地缓存

**问题描述**: 
项目标准是 L1 Caffeine + L2 Redis 双层缓存，config 模块仅使用 L2 Redis，每次查询都需要访问 Redis，增加网络开销。

**影响范围**: 
- 每次查询增加 1-5ms 网络延迟
- Redis 故障时缓存完全失效

**修复方案**:
1. 在 `CacheConfig.java` 中配置 `config` 缓存使用 Caffeine
2. 配置 L1 容量 10000 条，TTL 1 小时
3. 验证缓存命中率

**验证方法**:
- 压测：验证缓存命中时响应时间 <1ms
- 关闭 Redis，验证 L1 缓存仍然工作

**工作量**: 0.5 人日
