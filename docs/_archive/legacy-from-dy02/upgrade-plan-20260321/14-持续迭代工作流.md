# 持续迭代工作流（可自行慢慢完善）

> **性质**: 团队操作手册草案，非一次性定稿。每次迭代后更新 **§12 修订记录** 与勾选 **§10 清单**。  
> **对齐**: [11-方向基线与防漂移.md](11-方向基线与防漂移.md)（契约优先）· [10-内部运营体系战略规划.md](10-内部运营体系战略规划.md)（角色与节奏）· [13-五主播内容管线-详细规划与实施规格.md](13-五主播内容管线-详细规划与实施规格.md)（拍摄任务等）

---

## 1. 目标

用**固定节奏**把「内容产能 + 经营看数 + 系统能力」往前推，避免：

- 无验收标准的「想到哪改到哪」  
- 文档与代码长期脱节  
- 大改版推翻小改版（违背 `11` 的防漂移原则）

---

## 2. 迭代定义

**一次迭代** = 在一个时间盒内完成：**目标 → 交付 → 验收 → 复盘 → 更新文档/配置**，并留下可追溯记录（会议纪要、PR、变更记录表一项即可）。

不必追求「对话里刷 20 轮」；**10～20 次迭代**建议对应 **10～20 个时间盒**（例如 10～20 周），或 **§10 清单逐条攻克**。

---

## 3. 推荐节奏（可改，但团队内要统一）

| 层级 | 周期 | 做什么 |
|------|------|--------|
| **日站会** | 每日 10～15 分钟 | 阻塞项、今日拍摄/直播、爆款选题是否齐 |
| **内容周会** | 每周固定 1 次 | 五主播：上周成片/播放/转化口述 + 本周爆款库选题 3 条 |
| **产品/研发迭代** | **双周** 1 个时间盒（推荐） | 从 backlog 拉 1～3 个可验收项；合并必须过 `mvn compile` / `npm run type-check`（及你们 CI 约定） |
| **方向评审** | 每月或遇重大需求 | 对照 `11`：是否动契约（`live_format`、脚本类型、二创状态机等）；动则先改 `11` 再写代码 |

---

## 4. 单次迭代（双周盒）标准流程

```
0 立项 — 从 backlog 选条目，写清「用户/角色 + 成功样例 + 不做范围」
1 对齐 — 是否触碰 11 §2 契约？是则先修订 11 + OpenAPI/VO 草案
2 设计 — 必要时分文档（本目录或 modules/*）；接口路径与现有 POST 规范一致
3 实现 — 小步 PR，避免巨型合并
4 自测 — 后端编译 + 前端类型检查；关键路径手动点一遍
5 验收 — 对照 §6 验收口径（可裁剪）
6 复盘 — 5～10 分钟：什么有效、下轮停做什么
7 归档 — 更新 04-文档代码同步清单.md（若涉及清单内场景）、本文 §12
```

---

## 5. 双轨分工（与 `11` 一致）

| 轨道 | 本迭代要回答 | 典型交付物 |
|------|----------------|------------|
| **内容产能轨** | 策划/二创/拍摄是否断档？ | SOP 勾选、拍摄任务数、脚本生成次数、爆款采纳数 |
| **经营看数轨** | GMV/场次/实时是否可见？ | Dashboard 或列表字段、复盘用的导出/截图 |

**一条 PR 尽量只强归属其中一轨**；若两条都动，拆成两个用户故事或两个子 PR，便于验收。

---

## 6. 最小验收口径（每迭代至少选 2 条）

1. 相关页面或接口 **可访问、无 500**  
2. **owner/数据隔离**未被破坏（沿用现有 `DataScope` 行为）  
3. 若改 **错误码 / 表结构 / 配置含义**：已对照 `docs/development/04-文档代码同步清单.md`  
4. 若改 **API**：前端 `api/*.ts` 或调用方已同步  
5. **Flyway**：新迁移只新增序号，不改已发布脚本内容  

（可按团队加重：E2E、JaCoCo 门槛等，见 `docs/quality/`。）

---

## 7. Backlog 条目写法（模板）

```text
标题：［轨道：内容|看数］一句话
背景：业务痛点（1～2 句）
验收：可观察结果（列表）
契约：是否动 11 §2 / DB / ErrorCode（是/否）
依赖：无 / 依赖 xxx
估时：S|M|L
```

---

## 8. 与内部运营（`10`）的衔接

- **角色未落地前**：迭代仍以 admin/institution/talent 现有权限为准；功能设计预留 `roleCode` 扩展。  
- **六角色落地后**：每条 backlog 注明 **主角色**（运营/主播/摄影师等），验收时用该角色账号过一遍。

---

## 9. AI / 进化引擎的使用边界

- **知识进化**（`EvolveScheduler` 等）：适合 **知识库、主题、报告** 的周期性优化，不等于自动改业务代码。  
- **用 Cursor/大模型写代码**：默认 **人机在环**；合并前必须本地或 CI 编译通过。  
- **禁止默认**：无人值守自动合并进主分支、自动改生产配置。

## 10. 持续改进清单（20 项，可逐轮勾选）

> 不必按顺序；每完成一项在下方打 `[x]`，并在 §12 记日期与说明。

- [ ] **C01** 双周迭代节奏写入团队日历（固定周几）  
- [ ] **C02** Backlog 统一放一处（飞书/Notion/GitHub Projects 任选）  
- [ ] **C03** 每次发版更新 `14` §12 修订记录  
- [ ] **C04** 内容周会：爆款库每周至少入库/分析 **N** 条（自定 N）  
- [ ] **C05** 拍摄任务：每周关闭率 / 超期任务数有统计  
- [ ] **C06** 二创 SOP：爆款 → `viral_clone` 脚本 → 任务单 路径全员知晓  
- [ ] **C07** 直播：`session_type` 与规划中的 `live_format` 分工已评审并写入 `11`  
- [ ] **C08** Dashboard：GMV 或替代指标至少一个角色首页可见（对齐 `01`/`10`）  
- [ ] **C09** 实时面板：中控断网场景测一次（PWA/离线，见 `08`）  
- [ ] **C10** 脚本策划：分步向导上线或排期明确（见 `03`）  
- [ ] **C11** 错误提示：关键接口失败有可理解文案 + 重试或引导（见 `09` D8）  
- [ ] **C12** 新人：5 分钟「第一次创建场次/任务」说明（图文即可）  
- [ ] **C13** 配置漂移：`application.yml` 关键开关有表格说明（或指向文档）  
- [ ] **C14** 数据：重要指标口径写清（GMV 统计范围、时间字段）  
- [ ] **C15** 复盘模板：每周 3 个问题（最好一条、最差一条、下轮停做一件）  
- [ ] **C16** 爆款二创：`sv_viral_video` 状态机或工单与 `11` §2.3 一致  
- [ ] **C17** 企微：至少一条固定推送跑通（晨报或拍摄提醒）  
- [ ] **C18** 权限：摄影师仅改自己任务的状态/素材（若需要则单独立项）  
- [ ] **C19** AI 参考成片：配额与谁有权点击生成，写成制度  
- [ ] **C20** 季度：对照 `11` 全文做 **防漂移审计**（契约是否仍成立）
