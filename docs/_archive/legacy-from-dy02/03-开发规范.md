> 版本：3.1 | 更新日期：2026-02-26

## 一、新模块开发流程（9 步）

每个新模块**严格按此顺序**：

```
步骤 1 → 撰写模块设计文档（docs/modules/<模块>/xxx-模块设计文档.md）
步骤 2 → 编写 SQL（sql/<模块>/schema.sql + views.sql + demo.sql）
步骤 3 → 执行 SQL 建表
步骤 4 → 编写 Entity（@Entity + @Table + @Data + 逻辑删除 + 自动时间）
步骤 5 → 编写 Repository（extends JpaRepository + JpaSpecificationExecutor）
步骤 6 → 编写 VO（SearchVO + SaveVO + VO）
步骤 7 → 编写 Service 接口 + Impl（业务逻辑 + 事务）
步骤 8 → 编写 Controller（@RestController + @RequireLogin + RESTResult）
步骤 9 → 编写前端页面 + 注册资源（auth_resource + auth_role_resource）
```

## 三、后端规范

### 3.1 包结构

```
module/<模块名>/
├── controller/     XxxController.java
├── entity/         Xxx.java（对应数据库表）
├── repository/     XxxRepository.java
├── service/
│   ├── XxxService.java（接口）
│   └── impl/
│       └── XxxServiceImpl.java
└── vo/
    ├── XxxSearchVO.java（查询参数，继承 BasicQueryDto）
    ├── XxxSaveVO.java（保存入参，@Valid 校验）
    └── XxxVO.java（返回值）
```

### 3.2 Entity 规范

```java
@Data
@Entity
@Table(name = "表名")
@SQLRestriction("deleted = 0")
public class Xxx {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // 业务字段...

    @Column(name = "deleted", nullable = false)
    private Integer deleted = 0;

    @Column(name = "create_time")
    private Timestamp createTime;

    @Column(name = "update_time")
    private Timestamp updateTime;

    @PrePersist
    public void prePersist() {
        if (createTime == null) createTime = new Timestamp(System.currentTimeMillis());
        if (updateTime == null) updateTime = new Timestamp(System.currentTimeMillis());
    }

    @PreUpdate
    public void preUpdate() {
        updateTime = new Timestamp(System.currentTimeMillis());
    }
}
```

### 3.3 Controller 规范

```java
@RestController
@RequestMapping("/api/v1/<模块>/<资源>")
public class XxxController {

    @Resource
    private XxxService xxxService;

    @RequireLogin
    @PostMapping("/list")
    public RESTResult<PageResultVO<XxxVO>> list(@RequestBody(required = false) XxxSearchVO vo) {
        return RESTResult.getSuccess(xxxService.search(vo));
    }

    @RequireLogin
    @PostMapping("/save")
    public RESTResult<Long> save(@Valid @RequestBody XxxSaveVO vo) {
        return RESTResult.addSuccess(xxxService.save(vo));
    }
}
```

### 3.4 Service 规范

- 接口在 `service/XxxService.java`，实现在 `service/impl/XxxServiceImpl.java`
- 写操作加 `@Transactional(rollbackFor = Exception.class)`
- 跨模块调用**只通过 Service 接口**，不直接依赖其他模块的 Entity/Repository
- 业务异常抛 `BusinessException(ErrorCode.xxx, "消息")`

### 3.4.1 API 风格说明

项目默认采用**统一 POST + RPC 风格**（`/api/v1/<模块>/<资源>/<动作>`），所有查询和操作均使用 POST 方法。

**例外：live 模块**采用 RESTful 风格（GET/PUT/DELETE + 资源路径），原因：
- live 模块的场次/产品/话术具有明确的资源层级关系（session → products → scripts）
- RESTful 嵌套路径更直观地表达资源归属（`/sessions/{id}/scripts/{scriptId}`）
- 该模块在早期设计阶段确定，后续新模块应遵循统一 POST 规范

> **新模块开发时，必须使用统一 POST 风格，不得参照 live 模块的 REST 风格。**

### 3.5 数据隔离规范

所有用户私有数据的查询和操作**必须强制 owner_id 过滤**：

```java
// Service 层 —— 查询时强制加 owner_id 条件
public PageResultVO<XxxVO> search(XxxSearchVO vo) {
    Long userId = AuthTokenFilter.getUserId();
    // Specification 中强制添加 owner_id = userId
    spec = spec.and((root, query, cb) -> cb.equal(root.get("ownerId"), userId));
    // ...
}

// Service 层 —— 更新/删除时校验归属
public void delete(Long id) {
    Long userId = AuthTokenFilter.getUserId();
    Xxx entity = repository.findById(id)
        .orElseThrow(() -> new BusinessException(ErrorCode.DATA_NOT_FOUND, "数据不存在"));
    if (!entity.getOwnerId().equals(userId)) {
        throw new BusinessException(ErrorCode.FORBIDDEN, "无权操作");
    }
    entity.setDeleted(1);
    repository.save(entity);
}
```

**需要 owner_id 隔离的表：** dy_account, dy_persona, dy_product, sv_video, sv_video_data, sv_plan, sv_plan_asset, sv_viral_video, sv_comment, live_session, live_session_script, sc_script, sc_user_violation_word, sc_script_template（user 类型）, cp_library, cp_approval, sys_file, wc_robot_config, wc_push_rule, wc_message_log, agent（user_id）, agent_conversation（user_id）

**不需要 owner_id 的表（平台级）：** auth_*, sys_config*, sys_industry, sys_log_*, sc_violation_word（公共库）, sv_hot_topic, sv_category, live_script_template, cp_template（系统模板）, ab_experiment, ab_variant, ab_event

**多角色数据范围（DataScopeService）：**

系统有四种角色，数据可见范围不同：

| 角色 | 数据范围 | 实现方式 |
|------|----------|----------|
| admin | 所有数据 | 不加 owner_id 过滤 |
| institution | 自己 + 旗下所有达人的数据 | 通过 auth_org_member 查询成员 user_id 列表，`WHERE owner_id IN (visibleUserIds)` |
| talent | 仅自己的数据 | `WHERE owner_id = currentUserId` |
| user | 仅自己的数据 | `WHERE owner_id = currentUserId` |

```java
// DataScopeService 核心逻辑
public List<Long> getVisibleUserIds(Long currentUserId, String roleCode) {
    if ("admin".equals(roleCode)) return null; // null = 不限制
    if ("institution".equals(roleCode)) {
        // 查 auth_org_member 获取旗下达人 user_id 列表 + 自己
        List<Long> memberIds = orgMemberRepository.findUserIdsByOrgOwnerId(currentUserId);
        memberIds.add(currentUserId);
        return memberIds;
    }
    return List.of(currentUserId); // talent/user 只看自己
}
```

> **使用方式：** 所有需要 owner_id 隔离的 Service 层查询，注入 DataScopeService，用 `getVisibleUserIds()` 替代硬编码 `owner_id = currentUserId`。

**AI 模块数据隔离说明：** AI 模块的表采用 `user_id`（而非 `owner_id`）记录操作用户，属于**平台级共享数据**，不做 owner_id 行级隔离。具体策略：

| AI 表 | 隔离字段 | 隔离策略 | 说明 |
|--------|----------|----------|------|
| ai_call_log | user_id | 按用户过滤 | 用户只能查看自己的调用日志 |
| ai_call_quota | user_id | 按用户过滤 | 用户只能查看自己的额度 |
| ai_user_feedback | user_id | 按用户过滤 | 用户只能查看自己的反馈 |
| ai_model_config | — | 管理员专属 | 全局模型配置，仅管理员可操作 |
| ai_prompt_template | created_by | 管理员专属 | 全局模板，created_by 仅用于审计追踪 |
| ai_task_model_mapping | — | 管理员专属 | 全局任务-模型映射 |
| ai_knowledge / kb_document | — | 按 space 隔离 | 知识库按 space（项目空间）隔离，非按用户 |
| ai_evolve_* | — | 平台级 | 进化引擎为全局知识服务，无需用户隔离 |
| ai_index_queue | — | 平台级 | 索引队列为内部管道，无需用户隔离 |
| ai_viral_analysis | — | 平台级 | 爆款分析结果全局共享 |

> **设计原因：** AI 模块的核心价值在于知识共享和模型复用，按 owner_id 隔离会破坏知识库的全局检索能力。用户私有数据（调用日志、额度、反馈）通过 `user_id` 字段过滤，管理类数据通过角色权限控制。

### 3.6 缓存规范

系统使用 **Caffeine 本地缓存 + Redis 分布式缓存** 双层架构。

```java
// L1: Caffeine 本地缓存（进程内，毫秒级响应）
// 1. 系统配置缓存 —— 写时刷新（ConfigService 中维护）
private final Map<String, String> configCache = new ConcurrentHashMap<>();

// 2. 违规词库缓存 —— TTL 5 分钟（ViolationService 中维护）
private final Cache<String, List<ViolationWord>> violationCache = Caffeine.newBuilder()
    .expireAfterWrite(5, TimeUnit.MINUTES)
    .build();

// 3. AI 模型配置缓存 —— 写时刷新

// L2: Redis 分布式缓存（跨实例共享，AI 检索场景）
// 4. 知识库检索缓存 —— key: cache:kb:query:{hash}, TTL=3600s
// 5. 嵌入向量缓存 —— key: cache:kb:embed:{hash}, TTL=7200s
// 6. 分布式索引锁 —— key: lock:kb:index:{id}, TTL=300s
// 7. AI 幂等去重 —— key: cache:ai:request:{requestId}, TTL=86400s
```

**缓存规则：**

| 缓存层 | 场景 | 策略 | TTL | 刷新方式 |
|--------|------|------|-----|----------|
| L1 Caffeine | 系统配置 | Write-through | 无过期 | 修改时主动刷新 |
| L1 Caffeine | 公共违规词库 | TTL | 5 分钟 | 自动过期重载 |
| L1 Caffeine | AI 模型配置 | Write-through | 无过期 | 修改时主动刷新 |
| L1 Caffeine | 任务-模型映射 | Write-through | 无过期 | 修改时主动刷新 |
| L2 Redis | 知识库检索 | TTL | 可配置（默认 1h） | 自动过期 |
| L2 Redis | 嵌入向量 | TTL | 2h | 自动过期 |
| L2 Redis | 分布式锁 | TTL | 5min | 自动释放 |
| L2 Redis | AI 幂等去重 | TTL | 24h | 自动过期 |

> **降级策略：** Redis 不可用时，自动降级为仅使用 Caffeine 本地缓存，AI 检索跳过缓存直接查询。

### 3.7 异步处理规范

对于耗时操作（AI 生成、文件处理、数据同步），使用 **Spring @Async** + 状态追踪：

```java
// 1. 启用异步（Application 类）
@EnableAsync

// 2. 异步线程池配置
@Configuration
public class AsyncConfig {
    @Bean("aiTaskExecutor")
    public Executor aiTaskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4);
        executor.setMaxPoolSize(8);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("ai-task-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.initialize();
        return executor;
    }
}

// 3. 异步方法
@Async("aiTaskExecutor")
public void generateVideoAsync(Long taskId, GenerateParams params) {
    // 更新状态为 processing
    // 执行耗时操作
    // 更新状态为 completed / failed
}
```

**异步任务场景：**

| 场景 | 线程池 | 说明 |
|------|--------|------|
| AI 文本生成（短文案） | 同步 | < 5s，前端等待 |
| AI 复杂分析（爆款拆解） | aiTaskExecutor | 5-30s，轮询状态 |
| AI 多媒体生成（图/视频/TTS） | aiTaskExecutor | 分钟级，异步回调 |
| 知识自进化任务 | evolveTaskExecutor | 后台定时，独立线程池 |
| 知识库索引 | indexTaskExecutor | 异步入库，独立线程池 |
| 数据同步（抖音 API） | syncTaskExecutor | 定时同步，独立线程池 |

## 四、SQL 规范

### 4.1 文件组织

```
sql/<模块>/
├── schema.sql          表结构（CREATE TABLE）
├── views.sql           视图（CREATE VIEW），可选
├── resource-data.sql   菜单/API/按钮资源注册（INSERT INTO auth_resource）
└── demo.sql            演示数据（仅开发/测试环境）
```

### 4.2 建表模板

```sql
-- ============================================================
-- 表名: xxx_table
-- 说明: 表的用途
-- 模块: 所属模块
-- ============================================================
CREATE TABLE IF NOT EXISTS xxx_table (
    id            BIGSERIAL PRIMARY KEY,
    -- 业务字段
    name          VARCHAR(128) NOT NULL,
    status        INTEGER NOT NULL DEFAULT 1,
    -- 数据隔离
    owner_id      BIGINT,
    -- 逻辑删除 + 时间戳
    deleted       INTEGER NOT NULL DEFAULT 0,
    create_time   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    update_time   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

COMMENT ON TABLE xxx_table IS '表说明';
COMMENT ON COLUMN xxx_table.name IS '字段说明';
```

### 4.3 执行顺序

模块之间有依赖关系，SQL 必须按以下顺序执行：

```
P0 基础层（无依赖）:
  auth → log → config → storage → system

P0 业务层（依赖 auth + config）:
  douyin → ai

P1 核心业务（依赖 auth + douyin + ai）:
  script → shortvideo → live

P2 增值功能（依赖 P1 模块）:
  copy → product → abtest → agent → wecom
```

每个模块内的执行顺序：`schema.sql` → `views.sql` → `demo.sql` → `resource-data.sql`

> **注意：** product（产品管理）属于 douyin 模块，不是独立模块，其表结构在 `sql/douyin/schema.sql` 中。

### 4.4 跨模块 FK 约束规范

跨模块的外键引用**不使用数据库 FK 约束**（避免模块间强耦合），改为**应用层校验**：

```java
// 跨模块 FK 校验模式（Service 层）
// 例：live_session.account_id → dy_account.id
DyAccount account = dyAccountService.findById(vo.getAccountId());
if (account == null) {
    throw new BusinessException(ErrorCode.ACCOUNT_NOT_FOUND, "抖音账号不存在");
}
if (!account.getOwnerId().equals(currentUserId)) {
    throw new BusinessException(ErrorCode.FORBIDDEN, "无权操作该账号");
}
```

**跨模块 FK 引用清单：**

| live_session.persona_id | → | dy_persona.id | 人设属于当前用户 |
| live_session_product.product_id | → | dy_product.id | 产品属于同一账号 |
| live_session_script.ai_call_log_id | → | ai_call_log.id | 日志存在（AI 归因链） |
| sv_video.account_id | → | dy_account.id | 账号属于当前用户 |
| sv_plan.persona_id | → | dy_persona.id | 人设属于当前用户 |
| sv_plan.source_video_id | → | sv_video.id | 视频属于当前用户 |
| sv_plan.linked_video_id | → | sv_video.id | 视频属于当前用户 |
| sv_plan.ai_call_log_id | → | ai_call_log.id | 日志存在（AI 归因链） |
| sv_viral_video.industry_id | → | sys_industry.id | 行业存在且启用 |
| sv_viral_video.analysis_report_id | → | ai_viral_analysis.id | 分析报告存在 |

### 4.5 事务与部分失败模式

```java
// 模式 1：全量事务（配置保存、角色授权等原子操作）
@Transactional(rollbackFor = Exception.class)
public void batchSave(List<ConfigSaveVO> items) {
    // 全部成功或全部回滚
}

// 模式 2：尽力执行（整场话术生成、批量导入等可容错操作）
public BatchResult batchGenerate(List<Long> productIds) {
    BatchResult result = new BatchResult();
    for (Long productId : productIds) {
        try {
            generateForProduct(productId);
            result.addSuccess(productId);
        } catch (Exception e) {
            result.addFailed(productId, e.getMessage());
            log.warn("产品话术生成失败: productId={}", productId, e);
        }
    }
    return result; // 返回成功数 + 失败数 + 失败详情
}
```

### 5.4 异步任务前端交互模式

对于耗时的异步操作（AI 多媒体生成等），前端采用**提交 → 轮询 → 完成**模式：

```javascript
// 1. 提交异步任务
request('ai/media/generate', {
  data: params,
  success: function(taskId) {
    // 2. 开始轮询任务状态
    pollTaskStatus(taskId);
  }
});

// 3. 轮询直到完成
function pollTaskStatus(taskId) {
  var timer = setInterval(function() {
    request('ai/media/status', {
      data: { taskId: taskId },
      success: function(result) {
        if (result.status === 'completed') {
          clearInterval(timer);
          // 展示结果
        } else if (result.status === 'failed') {
          clearInterval(timer);
          Toast.error(result.message);
        }
        // else: pending/processing，继续轮询
      }
    });
  }, 3000); // 每 3 秒轮询一次
}
```
