## 总体原则

1. 先补“回归入口”，后拆“大文件”。
2. 先做高频主链，再做边缘功能。
3. 先补 service/页面 smoke，再追求深层覆盖率。
4. 每轮都维持 `npm run type-check` 通过；后端优先保持新增目标测试通过。
5. 不追求一次性 100% 覆盖，优先建立稳定的自动化基线。

## 阶段计划

### Phase 1：完成全模块基础回归入口

目标：每个有独立前端页面或 API 的核心模块，至少具备一层 API 测试和一层页面 smoke。

剩余重点：
- `live`：继续补列表/子页 smoke，扩大到工作台外围页
- `shortvideo`：补 `ProjectsPage` 之外的工作台、素材、发布页 smoke
- `ai`：补 `KnowledgeBasePage`、`AiDashboardPage` 之外的管理页 smoke
- `wecom`：补 `RulesPage`、`WecomPage` 之外的模板/日志页 smoke
- `log`：补 `AuditLogPage` 后，扩到 `SystemLogPage`

退出标准：
- 核心业务模块页面不再存在“完全无 smoke”的情况
- 所有已补模块都保持 `type-check` 通过

### Phase 2：重页面拆分与可测化

目标：降低超大文件的维护成本，把难测页面拆成“容器 + 纯展示 + hook”结构。

优先拆分文件：
- `live/ScriptTabContent.tsx`
- `live/GenerateTabContent.tsx`
- `payment/SubscriptionPage.tsx`
- `wecom/WecomPage.tsx`
- `script/ScriptListPage.tsx`
- `copy/CopyLibraryPage.tsx`
- `douyin/AccountsPage.tsx`
- `product/ProductsPage.tsx`
- `ai/EvolutionPage.tsx`
- `attribution/AttributionPage.tsx`

拆分策略：
- 提取纯展示组件
- 提取 query/mutation orchestration hook
- 提取图表 option builder / formatter / constants
- 减少页面组件中的行内匿名函数和混合状态

退出标准：
- 上述重页面至少拆掉前 6 个
- 每个被拆页面新增至少 1 个页面 smoke + 1 组逻辑测试

### Phase 3：后端 service 覆盖率补强

目标：补足高复杂模块的 service 层保护，降低重构风险。

优先级：
- P0：`ai / live / shortvideo`
- P1：`product / script / benchmark / storage`
- P2：`auth / system / messaging / payment / wecom`

优先测试类型：
- 参数校验
- 分支降级/错误码
- 外部依赖回退
- 缓存命中/未命中行为
- 事务性关键路径

退出标准：
- 每个 P0 模块新增至少 5 个 service/impl 测试文件
- 每个 P1 模块新增至少 2 个 service/impl 测试文件

### Phase 4：文档基线彻底收敛

目标：清掉“旧阶段口径”和当前实现的偏差。

重点：
- 统一 `dy01` → `dy02` 的当前说明文档
- 明确哪些文档是历史设计稿，哪些是当前运行基线
- 对每个 `docs/analysis/*` 文档加“校正说明”或替换为新基线

退出标准：
- 所有仍会被直接拿来指导开发/部署/测试的文档，都不再出现核心事实漂移

### Phase 5：CI 门禁与自动化执行

目标：把当前补出来的回归入口转成持续保障，而不是一次性劳动。

建议门禁：
- 前端：`npm run type-check`
- 前端：关键 API/页面 smoke 批次
- 后端：精选 service/controller 测试批次
- 后端：高价值集成测试分批执行

退出标准：
- 形成可稳定执行的 smoke 批次清单
- 新增页面/模块默认要求补对应 smoke 或 API 测试
