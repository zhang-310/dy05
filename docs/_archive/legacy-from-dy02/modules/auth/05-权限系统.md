# auth 模块 — RBAC 权限系统

> 版本：3.0 | 更新日期：2026-02-26

---

## 1. RBAC 模型说明

auth 模块采用简化的 RBAC（Role-Based Access Control）模型：

```
┌──────────┐     ┌──────────┐     ┌──────────────┐
│ auth_user│     │auth_role │     │auth_resource │
│          │     │          │     │              │
│ role_code├────→│ role_code│     │ resource_type│
│          │     │          │     │ resource_code│
│          │     │    id    ├──┐  │ parent_id    │
└──────────┘     └──────────┘  │  └──────────────┘
                               │         ↑
                          ┌────┴─────────┴────┐
                          │auth_role_resource  │
                          │                    │
                          │ role_id            │
                          │ resource_id        │
                          └────────────────────┘
```

**模型特点：**
- 一个用户对应一个角色（通过 role_code 直接关联，非多对多）
- 一个角色对应多个资源（通过 auth_role_resource 多对多关联）
- 资源分三种类型：menu（菜单）、api（接口）、button（按钮）
- admin 角色为超级管理员，跳过所有权限校验

## 2. 角色体系

### 2.1 预置角色

| 角色编码 | 角色名称 | 权限范围 | sort_order |
|---------|---------|---------|------------|
| admin | 平台管理员 | 全局管理，可访问所有接口，跳过权限校验 | 1 |
| institution | 机构管理员 | 管理旗下达人，查看机构范围内所有数据 | 5 |
| talent | 达人/主播 | 核心运营功能，仅可操作自己的数据 | 8 |
| user | 普通用户 | 仅个人数据操作 | 10 |

### 2.2 角色权限边界

```
admin（平台管理员）
├── 所有管理端接口（/api/v1/auth/user/*, /api/v1/auth/role/*, /api/v1/auth/resource/*）
├── 所有用户端接口
├── 所有菜单可见
├── Dashboard 接口：/api/v1/dashboard/admin
└── AuthPermissionService.hasPermission() 直接返回 true

institution（机构管理员）
├── 机构管理接口（/api/v1/organization/*）
│   ├── 创建/更新机构信息
│   ├── 邀请达人加入机构
│   ├── 移除机构成员
│   └── 查看机构成员列表
├── 业务数据接口（可查看旗下所有达人的数据）
│   ├── 抖音账号管理（自己 + 旗下达人）
│   ├── 短视频管理、直播管理、文案管理、话术管理、商品管理
│   └── 数据分析
├── Dashboard 接口：/api/v1/dashboard/org
└── 数据范围：DataScopeService 返回自己 + 旗下达人 userId 列表

talent（达人/主播）
├── 核心运营接口（仅自己的数据）
│   ├── 抖音账号管理
│   ├── 短视频管理（脚本创作、自动成片、每日任务、创作库）
│   ├── 直播管理（场次、商品、脚本）
│   ├── 话术库
│   └── 文案管理（文案库、文案模板）
├── 邀请处理接口
│   ├── 查看待处理邀请（/api/v1/organization/invitations）
│   ├── 接受邀请（/api/v1/organization/invitation/accept）
│   └── 拒绝邀请（/api/v1/organization/invitation/reject）
├── Dashboard 接口：/api/v1/dashboard/talent
└── 数据范围：DataScopeService 返回仅自己的 userId

user（普通用户）
├── POST /api/v1/auth/profile          — 获取个人信息
├── POST /api/v1/auth/profile/update   — 修改个人资料
├── POST /api/v1/auth/profile/change-password — 修改密码
├── POST /api/v1/auth/menu/search      — 获取菜单树
├── POST /api/v1/auth/resource/search  — 获取可访问资源编码
├── POST /api/v1/auth/oauth/bindings   — 查询已绑定第三方
├── POST /api/v1/auth/oauth/bind       — 绑定第三方
└── POST /api/v1/auth/oauth/unbind     — 解绑第三方
```

## 3. 资源类型

### 3.1 三种资源类型

| 类型 | resource_type | 用途 | resource_code 示例 |
|------|--------------|------|-------------------|
| 菜单 | menu | 前端导航菜单，支持树形结构 | `/admin/auth/user` |
| 接口 | api | 后端 API 路径，用于接口级权限校验 | `/api/v1/auth/user/search` |
| 按钮 | button | 前端按钮/操作权限 | `auth:user:ban` |

### 3.2 资源树形结构（menu 类型）

```
auth 模块菜单树示例：

系统管理 (parent_id=0)
├── 用户管理 (parent_id=系统管理.id)
│   └── resource_code: /admin/auth/user
├── 角色管理 (parent_id=系统管理.id)
│   └── resource_code: /admin/auth/role
└── 资源管理 (parent_id=系统管理.id)
    └── resource_code: /admin/auth/resource
```

## 4. 权限校验流程

### 4.1 整体流程

```
HTTP 请求
  │
  ▼
AuthTokenFilter（OncePerRequestFilter）
  │
  ├── 路径在 WHITELIST? → 直接放行（不校验 Token）
  │
  ├── 解析 Authorization Header
  │   ├── 无 Header → 2001
  │   ├── Token 无效 → 2003
  │   └── Token 过期 → 2001
  │
  ├── Token 有效 → 设置 SecurityContext
  │   │  (userId, username, roleCode)
  │   │
  │   ▼
  │  AuthPermissionService.hasPermission(roleCode, requestPath)
  │   │
  │   ├── roleCode = "admin" → true（超级管理员跳过）
  │   │
  │   ├── 查询该角色已授权的 api 类型资源
  │   │   SELECT r.resource_code FROM auth_resource r
  │   │   JOIN auth_role_resource rr ON r.id = rr.resource_id
  │   │   JOIN auth_role ro ON ro.id = rr.role_id
  │   │   WHERE ro.role_code = ? AND r.resource_type = 'api'
  │   │
  │   ├── requestPath 在已授权列表中? → true（放行）
  │   │
  │   └── 不在列表中 → 2002（NO_PERMISSION）
  │
  └── 放行 → Controller 处理请求
```

### 4.2 AuthTokenFilter 关键代码逻辑

```
public class AuthTokenFilter extends OncePerRequestFilter {

    // 白名单路径（免认证）
    private static final List<String> WHITELIST = List.of(
        "/api/v1/auth/login",
        "/api/v1/auth/captcha",
        "/api/v1/auth/sms/send",
        "/api/v1/auth/forgot-password",
        "/api/v1/auth/oauth/authorize",
        "/api/v1/auth/oauth/callback"
    );

    @Override
    protected void doFilterInternal(request, response, filterChain) {
        String path = request.getRequestURI();

        // 1. 白名单放行
        if (WHITELIST 匹配 path) {
            filterChain.doFilter(request, response);
            return;
        }

        // 2. 解析 Token
        String token = 从 Authorization Header 提取;
        TokenInfo info = authTokenStore.getToken(token);

        // 3. Token 校验
        if (info == null || info.isExpired()) {
            返回 2001 或 2003;
            return;
        }

        // 4. 设置用户上下文
        SecurityContext.set(info.getUserId(), info.getUsername(), info.getRoleCode());

        // 5. 权限校验
        if (!authPermissionService.hasPermission(info.getRoleCode(), path)) {
            返回 2002;
            return;
        }

        // 6. 放行
        filterChain.doFilter(request, response);
    }
}
```

## 5. 角色授权管理

### 5.1 全删重建策略

角色授权更新采用"事务内全删重建"策略，而非增量更新：

```
POST /api/v1/auth/role/resources/save
{roleId: 1, resourceIds: [10, 20, 30]}

@Transactional 内执行：
1. DELETE FROM auth_role_resource WHERE role_id = 1
2. INSERT INTO auth_role_resource (role_id, resource_id) VALUES
   (1, 10), (1, 20), (1, 30)
```

**选择全删重建的原因：**
- 实现简单，无需计算差集
- auth_role_resource 无逻辑删除字段
- 数据量小（每角色通常 < 100 条资源），性能无影响
- 事务保证一致性

### 5.2 授权查询

```
POST /api/v1/auth/role/resources
{roleId: 1}

→ SELECT resource_id FROM auth_role_resource WHERE role_id = 1
→ 返回 [10, 20, 30]（资源 ID 列表）
```

## 6. 菜单树构建逻辑

### 6.1 获取当前用户菜单

```
POST /api/v1/auth/menu/search

流程：
1. 从 SecurityContext 获取当前用户 roleCode
2. roleCode = "admin"?
   → 查询所有 resource_type='menu' 且 deleted=0 的资源
3. roleCode != "admin"?
   → 查询该角色已授权的 resource_type='menu' 资源
4. 构建树形结构：
   → 按 parent_id 分组
   → 递归构建（parent_id=0 为根节点）
   → 按 sort_order 排序
5. 返回菜单树 JSON
```

## 7. 白名单机制

### 7.1 白名单路径

以下 6 条路径免认证，AuthTokenFilter 直接放行：

| # | 路径 | 方法 | 说明 |
|---|------|------|------|
| 1 | `/api/v1/auth/login` | POST | 登录（未登录用户需要访问） |
| 2 | `/api/v1/auth/captcha` | GET | 图片验证码（登录前获取） |
| 3 | `/api/v1/auth/sms/send` | POST | 发送验证码（登录/忘记密码前） |
| 4 | `/api/v1/auth/forgot-password` | POST | 忘记密码（未登录用户） |
| 5 | `/api/v1/auth/oauth/authorize` | GET | OAuth 授权 URL（登录前获取） |
| 6 | `/api/v1/auth/oauth/callback` | GET | OAuth 回调（第三方平台回调） |

### 7.2 白名单匹配规则

- 精确匹配路径（非前缀匹配）
- 不校验请求方法（GET/POST 均放行）
- 静态资源路径（/pages/\*, /assets/\*）由 Web 服务器处理，不经过 Filter

## 8. 数据隔离策略

### 8.1 DataScopeService

系统通过 `DataScopeService` 统一管理数据范围，根据角色决定可见的用户 ID 列表：

| 角色 | 数据范围 | DataScopeService 返回值 |
|------|---------|------------------------|
| admin | 可查看/操作所有用户数据 | `null`（不限制） |
| institution | 可查看自己 + 旗下所有达人的数据 | `[自己的userId, 达人1的userId, 达人2的userId, ...]` |
| talent | 仅可操作自己的数据 | `[自己的userId]` |
| user | 仅可操作自己的数据（profile、change-password） | `[自己的userId]` |

### 8.2 隔离实现

```
DataScopeService.getVisibleUserIds(currentUserId, roleCode):
  → admin: return null（不限制）
  → institution: 查询 auth_org_member 获取旗下达人 userId + 自己
  → talent/user: return [currentUserId]

Controller 层调用示例：
  List<Long> visibleIds = dataScopeService.getVisibleUserIds(userId, roleCode);
  if (visibleIds != null) {
      searchVO.setUserIds(visibleIds);  // Service 层 Specification 使用 IN 查询
  }
```

### 8.3 组织模型

```
auth_organization（机构表）
├── org_name     — 机构名称
├── org_code     — 机构编码（唯一）
├── owner_id     — 创建者（institution 角色用户）
└── status       — 1=正常 0=禁用

auth_org_member（机构成员表）
├── org_id       — 机构 ID
├── user_id      — 用户 ID（talent 角色）
├── role_in_org  — 机构内角色：owner / admin / member
└── status       — 0=待确认 1=已加入 2=已拒绝

auth_user.organization_id — 所属机构 ID（可空，达人可独立存在）
```

### 8.4 机构邀请流程

```
1. institution 用户创建机构 → auth_organization 记录
2. institution 搜索达人 → /api/v1/organization/search-talents
3. institution 发送邀请 → auth_org_member (status=0 待确认)
4. talent 查看邀请 → /api/v1/organization/invitations
5. talent 接受邀请 → auth_org_member.status=1, auth_user.organization_id 更新
6. talent 拒绝邀请 → auth_org_member.status=2
7. institution 移除成员 → auth_org_member.deleted=1, auth_user.organization_id 清空
```
