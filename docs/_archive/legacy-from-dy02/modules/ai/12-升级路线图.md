# AI模块 — 数据驱动升级路线图

> 版本：1.0 | 更新日期：2026-02-26 | 阶段：规划

---

## 升级核心理念

当前 AI 模块的进化引擎依赖 LLM 自生成报告作为知识来源，存在「自我循环」风险——模型吃自己的输出，知识库会逐渐同质化。

本系统已有完整的抖音真实数据链路（douyin 模块 OAuth 绑定 → shortvideo 视频数据回流 → live 直播时序数据），这些真实业务数据是比 LLM 生成内容有价值 100 倍的知识燃料。

**升级方向：让 AI 消化真实抖音数据产出知识，而不是凭空编写报告。**

## 一、效果归因链（P0 — 最高优先级）

### 1.1 问题

当前 AI 生成内容后，无法追踪该内容发布到抖音后的实际表现。没有归因，进化引擎就是「盲进化」。

### 1.2 方案

打通「AI 生成 → 用户发布 → 抖音数据回流 → 归因到知识条目」的完整链路。

```
AI 生成文案（记录引用的知识 chunk_ids）
    → 用户发布到抖音（关联 video_id / session_id）
    → VideoStatistics 每日快照回流
    → 定时归因任务：视频表现好 → 反向提升相关知识的 boost_factor
    → 进化引擎感知：这类主题有实战价值 → 加大该方向进化力度
```

### 1.3 数据库变更

**ai_call_log 新增字段：**

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| referenced_chunk_ids | TEXT | | — | 本次生成引用的知识条目 ID（JSON 数组） |
| linked_video_id | BIGINT | | — | 关联的短视频 ID（用户发布后回填） |
| linked_session_id | BIGINT | | — | 关联的直播场次 ID（用户发布后回填） |
| content_effect | VARCHAR(32) | | — | 内容效果：high_perform / normal / low_perform |
| effect_score | DECIMAL(8,2) | | — | 效果评分（播放量/均值的比值） |

**新增业务规则：**

| 编号 | 规则 | 说明 |
|------|------|------|
| BR-30 | 效果归因定时任务 | 每日 02:00 扫描「有 linked_video_id 且 content_effect 为空」的记录，从 VideoStatistics 拉取 7 天累计数据，计算 effect_score = 播放量 / 该账号近 30 天视频均值。> 1.5x 标记 high_perform，< 0.3x 标记 low_perform |
| BR-31 | 知识权重反向更新 | high_perform 的 referenced_chunk_ids 对应知识条目 boost_factor += 0.15；low_perform 对应 boost_factor -= 0.05 |
| BR-32 | 内容关联时机 | 用户在 shortvideo/live 模块发布内容时，前端传入 ai_call_log_id，后端回填 linked_video_id / linked_session_id |

### 1.4 接口变更

```
新增接口：POST /api/v1/ai/call-log/link
请求体：{ "callLogId": 123, "videoId": 456 }  或  { "callLogId": 123, "sessionId": 789 }
说明：用户发布内容后，前端调用此接口关联 AI 调用记录与实际发布内容
```

### 1.5 环境变量

| 变量名 | 级别 | 默认值 | 说明 |
|--------|------|--------|------|
| ATTRIBUTION_ENABLED | 🟡 推荐 | true | 是否启用效果归因 |
| ATTRIBUTION_CRON | 🟢 可选 | 0 0 2 * * ? | 归因定时任务 Cron |
| ATTRIBUTION_WAIT_DAYS | 🟢 可选 | 7 | 发布后等待多少天再归因（等数据稳定） |
| ATTRIBUTION_HIGH_THRESHOLD | 🟢 可选 | 1.5 | 高效内容阈值（播放量/均值） |
| ATTRIBUTION_LOW_THRESHOLD | 🟢 可选 | 0.3 | 低效内容阈值（播放量/均值） |

## 二、爆款拆解 Agent（P0）

### 2.1 问题

当前进化引擎的知识来源是 LLM 自生成报告。系统已有 VideoStatistics 每日快照数据，可以自动发现爆款视频并拆解成可复制的方法论。

### 2.2 方案

```
定时任务（每日 03:00）
    ↓
[爆款检测]
    ├─ 扫描所有绑定账号的 VideoStatistics
    ├─ 筛选条件：播放量 > 该账号近 30 天均值 × 3
    ├─ 排除已拆解的视频（ai_viral_analysis 已存在）
    └─ 输出：待拆解视频列表
    ↓
[数据收集]（每个爆款视频）
    ├─ ShortVideo：标题、描述、标签、发布时间、时长
    ├─ VideoStatistics：播放量增长曲线（每日快照）
    ├─ VideoComment：高赞评论 TOP 20（情感分析）
    ├─ 知识库检索：该视频主题相关的已有知识
    └─ 同账号历史视频：对比数据（为什么这条爆了）
    ↓
[LLM 拆解]
    ├─ Prompt：「基于以下真实数据，分析这条爆款视频的成功因素，提炼可复制的方法论」
    ├─ 输入：视频数据 + 评论数据 + 增长曲线 + 对比数据
    ├─ 输出：拆解报告（成功因素 + 可复制方法论 + 适用场景）
    └─ 模型：使用商业 API（拆解质量要求高）
    ↓
[质量评分 + 入库]
    ├─ 复用现有质量评分系统（100 分制）
    ├─ ≥ 50 分：入库（BGE-M3 嵌入 → Milvus + ES）
    └─ 标记 source='viral_analysis'，与普通进化报告区分
```

### 2.3 数据库变更

**新增表 ai_viral_analysis：**

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| id | BIGSERIAL | PK | 自增 | 主键 |
| video_id | BIGINT | NOT NULL | — | 关联 ShortVideo.id |
| account_id | BIGINT | NOT NULL | — | 关联 DouyinAccount.id |
| viral_score | DECIMAL(5,2) | | 0 | 爆款程度（播放量 / 账号均值） |
| view_count | BIGINT | | 0 | 视频播放量 |
| account_avg_views | BIGINT | | 0 | 账号近 30 天均值 |
| success_factors | TEXT | | — | 成功因素分析（JSON） |
| replicable_methods | TEXT | | — | 可复制方法论（JSON） |
| report_content | TEXT | | — | 完整拆解报告 |
| quality_score | DECIMAL(5,2) | | 0 | 质量评分 |
| index_status | VARCHAR(16) | | 'pending' | pending / indexed / skipped |
| create_time | TIMESTAMP | | CURRENT_TIMESTAMP | |

索引：`(account_id, create_time DESC)`、`(video_id)` UNIQUE、`(quality_score DESC)`

### 2.4 环境变量

| 变量名 | 级别 | 默认值 | 说明 |
|--------|------|--------|------|
| VIRAL_ANALYSIS_ENABLED | 🟡 推荐 | true | 是否启用爆款拆解 |
| VIRAL_ANALYSIS_CRON | 🟢 可选 | 0 0 3 * * ? | 爆款拆解定时任务 Cron |

## 三、直播复盘 Agent（P1）

### 3.1 问题

LiveMonitor 记录了直播全程的时序数据（每个时间点的观众/点赞/评论），LiveScript 记录了话术执行时间点。这两组数据关联分析，可以精确归因「哪句话术带来了观众增长」。

### 3.2 方案

```
触发条件：LiveSession.status 变为 ended（直播结束）
    ↓
[数据收集]
    ├─ LiveSession：总观众、总 GMV、总订单、时长
    ├─ LiveMonitor：时序数据（每 5s 一个点：观众/点赞/评论/分享）
    ├─ LiveProduct：各商品销售数据（数量/GMV/展示次数）
    ├─ LiveScript：话术执行记录（哪句话术在什么时间执行的）
    └─ 该账号历史直播数据（对比基准）
    ↓
[关联分析]（规则引擎，非 LLM）
    ├─ 话术-观众关联：话术执行后 30s 内观众变化（增/减/平）
    ├─ 话术-互动关联：话术执行后 30s 内评论/点赞变化
    ├─ 商品-转化关联：商品讲解时段的转化率
    ├─ 峰值分析：观众峰值出现在什么时间点，当时在做什么
    └─ 流失分析：观众大量离开的时间点，当时在做什么
    ↓
[LLM 复盘]
    ├─ Prompt：「基于以下直播真实数据和关联分析结果，生成直播复盘报告」
    ├─ 输入：关联分析结果 + 历史对比 + 知识库相关方法论
    ├─ 输出：复盘报告（亮点 + 问题 + 改进建议 + 下场直播话术建议）
    └─ 模型：使用商业 API
    ↓
[入库 + 推送]
    ├─ 高分报告入库（source='live_review'）
    ├─ 复盘报告推送到用户 Dashboard
    └─ 高效话术标记到 live_script_template.effectiveness_score
```

### 3.3 数据库变更

**新增表 ai_live_review：**

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|

| session_id | BIGINT | NOT NULL | — | 关联 LiveSession.id |
| account_id | BIGINT | NOT NULL | — | 关联 DouyinAccount.id |
| total_viewers | INTEGER | | 0 | 总观众数 |
| total_gmv | DECIMAL(12,2) | | 0 | 总 GMV |

| weak_points | TEXT | | — | 薄弱环节（JSON：时间段 + 问题描述） |
| report_content | TEXT | | — | 完整复盘报告 |
| improvement_suggestions | TEXT | | — | 改进建议（JSON 数组） |

| index_status | VARCHAR(16) | | 'pending' | pending / indexed / skipped |

索引：`(session_id)` UNIQUE、`(account_id, create_time DESC)`

## 四、查询改写 + 用户画像（P1）

### 4.1 问题

当前检索直接用用户原始查询做向量+关键词检索，没有结合用户的账号画像（粉丝量级、品类、历史数据），检索结果不够精准。

### 4.2 方案

在检索前增加一步 LLM 查询改写（1 次 API 调用，成本 < ¥0.01）：

```
用户输入：「直播间人少怎么办」
    ↓
[用户画像收集]（从 douyin 模块读取，非 LLM）
    ├─ DouyinAccount：粉丝数 5000，美妆类
    ├─ 最近 5 场 LiveSession：平均观众 50 人
    └─ 最近 10 条 ShortVideo：平均播放量 2000
    ↓
[LLM 查询改写]
    ├─ Prompt：「用户是粉丝 5000 的美妆主播，平均直播观众 50 人。
    │          将查询「直播间人少怎么办」改写为 2-3 个更精准的子查询」
    └─ 输出：
        1.「中小美妆主播直播间自然流量提升方法」
        2.「5000 粉丝级别直播间开播预热策略」
        3.「美妆直播间留人互动话术」
    ↓
[多路并行检索]
    ├─ 子查询 1 → RRF 混合检索 → Top 10
    ├─ 子查询 2 → RRF 混合检索 → Top 10
    └─ 子查询 3 → RRF 混合检索 → Top 10
    ↓
[结果融合去重]
    ├─ 合并 3 路结果，按 chunk_id 去重
    ├─ 重新 RRF 排序
    └─ Cross-Encoder 重排 → 返回 Top K
```

### 4.3 业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| BR-33 | 查询改写触发条件 | 仅当用户已绑定抖音账号时启用查询改写；未绑定时走原始查询 |
| BR-34 | 查询改写缓存 | 改写结果缓存 1h（key: cache:kb:rewrite:{sha256(query+accountId)}），避免重复调用 LLM |
| BR-35 | 查询改写降级 | LLM 改写超时 3s 或失败时，降级为原始查询直接检索 |

### 4.4 环境变量

| 变量名 | 级别 | 默认值 | 说明 |
|--------|------|--------|------|
| QUERY_REWRITE_ENABLED | 🟡 推荐 | true | 是否启用查询改写 |
| QUERY_REWRITE_TIMEOUT | 🟢 可选 | 3 | 查询改写超时（秒），超时降级为原始查询 |
| QUERY_REWRITE_SUB_QUERIES | 🟢 可选 | 3 | 改写子查询数量 |

## 五、进化引擎 ROI 监控（P1）

### 5.1 问题

进化引擎持续运行消耗 API 成本，但缺少衡量进化效果的指标。如果连续多轮进化的入库率很低，说明在空转。

### 5.2 方案

新增进化 ROI 监控指标：

| 指标 | 计算方式 | 告警阈值 |
|------|---------|---------|
| 单轮入库率 | 入库报告数 / 生成报告数 | < 30% 连续 3 轮 |
| 知识引用率 | 被检索引用的进化知识 / 总进化知识 | < 10%（30 天内） |
| 进化成本效率 | 进化总成本 / 入库报告数 | > ¥5/篇 |
| 数据驱动占比 | 爆款拆解+直播复盘入库数 / 总入库数 | 目标 > 40% |

**自动调频规则：**

| 编号 | 规则 | 说明 |
|------|------|------|
| BR-36 | 进化自动降频 | 连续 5 轮入库率 < 30% → 自动将进化频率从 24h 降为 48h，并通知管理员 |
| BR-37 | 进化自动恢复 | 降频后连续 3 轮入库率 ≥ 50% → 自动恢复 24h 频率 |

## 八、验收标准

- [ ] 效果归因链路跑通：AI 生成 → 发布 → 7 天后自动归因 → boost_factor 更新
- [ ] 爆款拆解：自动检测爆款视频 → 生成拆解报告 → 高分入库
- [ ] 直播复盘：直播结束 10 分钟后自动生成复盘报告
- [ ] 查询改写：绑定账号用户的检索结果相关性优于未改写
- [ ] 进化 ROI：连续低入库率时自动降频，恢复后自动提频
